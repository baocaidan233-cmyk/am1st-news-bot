# AM1ST（America First）新闻频道 — 运行规则文档

最后更新：2026-08-06

## 一句话说明

这是从原来的 n8n 自动化workflow迁移过来的 Python 版本。整个系统分成两个**完全独立、互不等待**的流程：一个负责抓新闻、筛选、生成文案、存起来；另一个每隔一段时间从存好的那批里挑一篇发出去。两个流程各自有自己的调度节奏，中间靠一个共享的 Notion 数据库（候选池）传递信息。

```
┌─────────────┐        写入候选池        ┌─────────────┐
│  抓取流程     │ ──────────────────────▶ │  候选池      │
│ main.py     │                          │ (Notion库)   │
│ 每10分钟一次  │                          └──────┬──────┘
└─────────────┘                                  │ 读取
                                                  ▼
                                          ┌─────────────┐
                                          │  发布流程     │
                                          │main_publish.py│
                                          │ 每30分钟一次  │
                                          └─────────────┘
```

## 一、抓取流程（`main.py`）

**调度**：每 10 分钟一轮（`poll_interval_seconds`），实际间隔会加 ±10% 随机抖动，避免和别的机器人同时打 API。

**每一轮按顺序做这些事，前面的步骤把稿子淘汰掉，后面就不用再处理，省钱省时间：**

1. **读信源列表**（Notion "rss_n8n_am1st_news" 库）——只处理 `in_use` 勾选为true 的行，里面记录着每个网站的 RSS 地址、付费墙 cookie（如果有）。

2. **抓 RSS**——用 feedparser 解析，时间统一转成 UTC。只留发布时间在最近 **3 小时**以内的（`max_publish_age_hours`）。如果某条的发布时间解析不出来，默认放行（宁可多留、不错杀）。

3. **去重第一层 —— Redis 精确查重**：对每条新闻的链接算哈希值，查 Redis 里有没有见过。见过就跳过，没见过就记下来，**保留 10 天**（`redis.ttl_seconds`）。这是最便宜的一层，先过滤掉明显重复的。

4. **去重第二层 —— 同一轮内语义查重**：把标题+摘要转成向量，跟这一轮已经通过的稿子两两比较，**余弦相似度 ≥ 0.8** 就算重复，跳过。防止同一轮里抓到好几个源都报道同一件事。

5. **去重第三层 —— 跨轮次语义查重**（Qdrant 向量库，collection `am1st_embeddings`）：跟**过去 72 小时**（`qdrant.cross_cycle_window_hours`）里写入过的标题+摘要向量比较，余弦相似度 **≥ 0.8**（`dedup.semantic_threshold`）算重复，跳过——这一步逻辑没变。

5.5. **事件聚合/热度计算**（`am1st_events` 这个单独的Qdrant库，2026-08-06新加，跟上面的查重是两次独立查询）：这一步**不管上一步判不判重复都会做**，而且**在判重复之前做**——因为哪怕这条最后被当重复丢掉，它也是"多一个信源在报道这件事"的证据，不能丢。做法参考了新闻聚类的成熟算法(TDT/Topic Tracking)：**一个"事件"不是一个固定向量，是一组共享同一个`event_id`的向量点**——新文章进来,跟这个库里所有代表点比对,只要有一个相似度**≥0.6**(`heat.related_threshold`)且是**10天以内**(`heat.window_hours`=240小时,跟Redis的10天惯例一致)还在更新的事件,就算命中:
   - 把这个事件的`heat_score`累加(主流媒体路透/FT/WSJ/CNN/CBS/FOX/纽约邮报/Just The News权重×2,其他信源×1,同一个信源不重复计分)、`first_seen_at`取更早的时间、`last_updated_at`刷新成现在——这三个值会同步更新到这个事件下**所有**代表点上,不会不一致。
   - 如果这条新文章**不是**重复(即将写进候选池),额外把它的向量**也加入这个事件的代表点**——这样以后哪怕后续报道用词跟最初那篇不像,只要跟这篇像,也能归到同一事件,不会被拆散成两个事件(这是"多代表向量"要解决的问题:固定用第一篇报道当锚点,容易因为措辞差异或事件演化几天后跟不上而误判成新事件)。
   - 如果这条新文章**是**重复(即将被上一步丢弃),不新增代表点(没有新增匹配价值),只更新热度数字。
   
   算出来的`heat_score`/`first_seen_at`存进候选池,喂给下面第6步的AI打分和发布流程第4步的AI重排序。

6. **AI 打分**（gpt-4o-mini）：给标题+摘要（外加上面算出来的 `heat_score`/`event_first_seen_at`）打分，**低于 5 分**（`openai.score_threshold`）的直接淘汰，不进入下一步（省下全文抓取和生成文案的成本）。

7. **全文提取**：用 httpx 抓网页正文 + trafilatura 解析。如果这个源配置了付费墙 cookie，会带上 cookie 一起请求。抓到的正文低于 **200 字**（`extraction.min_text_length`）算提取失败——按失败处理，同时会往 Notion 源库对应行的评论区 @你 提醒（有 6 小时冷却，`alert_cooldown_seconds`，不会同一个源一直刷屏提醒）。**目前 NYT/FT/Economist/Bloomberg/华盛顿邮报这几个付费墙网站还抓不到正文**（需要 Playwright，还没接）。

8. **生成发布文案**（gpt-4o-mini）：基于全文生成一段适合发到 Gettr 的文案。如果模型判断这条新闻不值得发（返回 "No comment"），直接过滤掉，不进候选池。

9. **写入候选池**（Notion 库，测试环境是 `am1st_news_log` 这张表复用来测试）：把标题、链接、作者、摘要、发布时间、正文、AI 打分、AI 评语、生成的文案、链接哈希、`heat_score`、`event_first_seen_at` 都存进去，`send_status` 留空（false）。同时把这条的标题+摘要向量写入 Qdrant（供步骤 5 未来查重/算热度用，写入时也带上信源名字，供以后判断"是不是主流媒体"）。

**这一步结束——抓取流程不会自己发布任何东西，纯粹是"攒稿子"。**

## 二、发布流程（`main_publish.py`）

**调度**：每 30 分钟一轮（`publish.interval_seconds`），同样带 ±10% 抖动。

**每一轮按顺序做：**

1. **查候选池**：条件是 `send_status ≠ true`（还没发过）、创建时间在 **12 小时以内**（`publish.candidate_max_age_hours`）、AI 打分 **≥ 6 分**（`publish.candidate_min_score`），按打分从高到低排序。

2. **过滤过期措辞**：关键词过滤掉那种明显过时的"前总统特朗普"式表述（这是直接照抄原来 n8n 里那条规则）。

3. **分层挑选一批（最多10篇，最少3篇——2026-08-05把上限从5提到10，因为全文提取/生成文案挪到这一步之后才做，多挑几篇也不费钱）**：
   - 判断今天是不是工作日（美东时区）：工作日新闻多，优先门槛用 `publish.weekday_min_score`=6 分；周末新闻少，直接用 `publish.weekend_min_score`=5 分门槛
   - 优先挑 **4 小时内**（`publish.fresh_hours`）且打分 **≥ 7** 的
   - 不够就放宽到 4 小时内、达到上面那个门槛的也算
   - 还不够就不管时效性，只要打分达到门槛的都算
   - 工作日专属兜底：还不够，放宽到周末的 5 分门槛
   - 实在凑不够，最后兜底：不管分数，直接拿**最新的几篇**
   - 最多凑够 10 篇（`publish.batch_max`）就停

4. **AI 重新排优先级**（gpt-4o-mini，第二次打分，这次是基于生成好的文案内容，不是标题摘要）：给这一批稿子重新打一个 1-10 的"优先级分"，重点是"现在这个时间点，哪篇最值得发"。同时会看 Google News 当前的美国政治热点标题（只读，一个免费、不用 API key 的信号，抓的是 NATION 板块），以及每篇稿子的两个新鲜度数字——`hours_old`(这件事整体存在了多久,来自`event_first_seen_at`)和`hours_since_update`(这篇具体报道自己发布了多久,2026-08-06新加)。这两个数字故意分开送,不合并成一个:一个持续几天的案子如果今天有新进展(新证据/新人物),这篇报道按`hours_since_update`是全新的,不该因为`hours_old`大就被当成旧闻打低分——只有当两个数字都大、且没有主流媒体热度支撑时,才真按旧闻处理。按最终分数从高到低排序。

5. **已发布查重**（Qdrant 向量库，collection `am1st_posting_news_embedding`，专门存"已经真正发出去的文案"，跟抓取阶段的向量库是两个完全不同的库）：把生成的文案转成向量，跟**过去 24 小时**（`publish.posted_dedup_window_hours`）内实际发布过的比较，**余弦相似度 > 0.70**（`publish.posted_dedup_threshold`）就算重复。**这个阈值比抓取阶段的 0.8 更严格**——因为这是机器全自动发布，宁可少发也不要发出明显重复的内容。

6. **按优先级顺序，从高到低找第一个不重复的**：遇到重复的就跳过（只打日志，不再单独记录到 Notion——8/5 决定简化掉了"记录跳过稿件"这个环节，之前设计是要记一笔日志，后来讨论后觉得没必要）。找到第一个不重复的就是这一轮的赢家。如果这批全都是重复的，这一轮就**不发**，不会硬凑一篇发出去。

7. **发布到 Gettr**（2026-08-05 接通，`agents/gettr_publisher.py`）：真的调用盖特发帖接口，用测试账号。

8. **标记已发**：只有真的发布成功才会：把候选池那一行的 `send_status` 改成 true，并把这条文案的向量写进"已发布"库供下次查重用。发布失败不会误标记、不会污染查重数据。

## 三、涉及的外部服务

| 服务 | 用途 | 备注 |
|---|---|---|
| Notion（源库） | 存 RSS 信源列表 | 用 `NOTION_API_KEY` 这个 key |
| Notion（候选池库） | 抓取流程写、发布流程读 | 用 `NOTION_CANDIDATE_API_KEY` 这个独立的 key，跟源库的integration 不是同一个 |
| Redis（Upstash） | 抓取阶段第一层去重（URL 哈希） | 10 天过期 |
| Qdrant | 三个独立 collection：`am1st_embeddings`（抓取侧跨轮次查重）+ `am1st_posting_news_embedding`（发布侧"已发布"查重）+ `am1st_events`（事件聚合/热度，2026-08-06新加） | 复用团队现有的共享集群，多个频道共用同一个集群、各自不同 collection |
| OpenAI（gpt-4o-mini） | 打分 ×2 次（抓取时、发布时）+ 生成文案 + embedding | |
| Gettr | 实际发帖 | 已接通（2026-08-05），用测试账号验证过真实发布成功 |
